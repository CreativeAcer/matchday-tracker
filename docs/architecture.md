# Architecture

## The whole thing

```
matchday-tracker/
├── index.html          the entire app: CSS, markup and JS in one file (~7,150 lines, ~350 KB)
├── sw.js               service worker: offline support
├── manifest.json       PWA manifest (name, icons, standalone display)
├── icon-192/512.png, icon-maskable-512.png, apple-touch-icon.png
├── screenshots/        images used by the README
├── android-shell/      Capacitor wrapper that packages index.html as an Android app
└── .github/workflows/android.yml   manual workflow that builds the APK
```

There is **no build step, no bundler, no framework and no runtime dependency** except the Google Fonts
stylesheet. Opening `index.html` in a browser runs the app. That is a feature: keep it.

## State and rendering model

- **One state object** `state` = `{ version: 2, teams: [...], activeTeamId }`. `T()` returns the active team
  and heals itself (never undefined). All code reads and writes `T()`.
- **Persist after every change**: `persist()` writes the whole state as JSON to `localStorage`. If the write
  fails (quota, private mode) a persistent warning tells the coach to export.
- **Render is a full redraw of the active screen**: `render()` shows/hides the three screens, repaints the
  top bar and clock, then regenerates the active screen's HTML. There is no virtual DOM and no diffing.
  Event handlers are wired after each render. State changes follow the pattern *mutate, `persist()`,
  `render()`*.
- **The clock face is the exception**: `paintClock` is the only writer of the clock digits. A one-second
  `setInterval`, running only while a clock runs, calls `checkStaleClock`, `checkPeriodEnd`, `paintClock`,
  `updateLiveMinutes` and `syncChrome` without a full render.
- **`view`** is one of `match`, `summary`, `team`, `history`. `summary` shows under the Match tab.
- **Match = state + event log.** A match is `activeMatch` with a list of `events`. Score, scorers, cards and
  minutes are *derived* (`computeStats`, `playingTimeMinutes`) and never stored separately while live.
  A finished match becomes a history record that does store the derived numbers, recomputed after any
  edit (`recomputeRecord`).
- **Time is read from `Date.now()`** each time (`clockElapsedMs`), not ticked and stored, so a locked or
  backgrounded phone loses nothing.

## Boot order (fragile, covered by tests)

At load, `load()` and `persist()` run **before** the first `render()`, and everything the render needs
(constants, helper functions) must be defined above the boot statements. Code that reads a not-yet-assigned
`var` at startup breaks every saved season silently. `tests/bootorder.js`, `bootreach54.js`,
`toplevel54.js` and `freefn.js` guard this. Do not add top-level statements after the boot block.

## Service worker (`sw.js`)

Goal: the app opens with no signal, and updates when there is signal.

- `CACHE_VERSION = "matchday-vNN"`, bumped on every deploy and equal to `APP_VERSION`.
- **Install is all-or-nothing for `./index.html`** (`CRITICAL`); icons, manifest and `./` are best effort
  (`OPTIONAL`). If the shell cannot be cached the new worker never activates and the old version keeps
  serving. A half-cached new version must never replace a working old one.
- **Activate deletes old caches only if the new cache really holds the app.**
- **Navigations are network-first** with the cache as offline fallback, and a successful navigation repairs
  the cached shell. Google Fonts are cache-first. Other same-origin files are cache-first with a background
  refresh.

## Native shell (Android, Capacitor)

`android-shell/` wraps the same `index.html` (no second code base). Differences: no service worker and no
install hint, fonts are bundled, share goes through the Android share sheet, a light haptic tick on counted
taps, the screen stays on while the clock runs, a buzz at the end of a period, and the back button closes a
sheet first and does nothing during a live match. The app detects the shell with `nativeBridge()` and uses
plugins (`Filesystem`, `Share`, `Haptics`) through `nativeCall`. All of it degrades to normal web behaviour
when the bridge is absent, so the same file serves both. See `release.md` for building.

## Constraints that shape every change

- Strict ES5 style: `var` and function declarations. The file contains no `let`, `const`, arrow functions or
  template literals, no modules and no transpiler. Keep it that way.
- No new runtime dependencies and no network calls. Data never leaves the device unless the coach shares a
  file or card.
- Backward-compatible state only (`data-model.md`).
- Anything new that persists must go through `normaliseTeam` (the one list of a team's fields).
